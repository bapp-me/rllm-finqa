  一、项目概述                                                                                                                                                                                                                                      
                                                                                                                                                                                                                                                    
  rLLM-FinQA 是 UC Berkeley rLLM 团队与 Snorkel AI 合作的金融问答项目。核心目标是通过强化学习（GRPO）训练一个 ReAct 风格的工具调用 Agent，使其能够回答基于 SEC 10-K 年报的定量金融问题。                                                            
                                                                                                                                                                                                                                                    
  核心成果： 仅 4B 参数的 rLLM-FinQA-4B 在 Snorkel FinQA 基准上达到 59.7% Pass@1，超越 Qwen3-235B（51.4%），接近 Gemini 2.5 Pro（60.6%）。训练总成本 < $500。

  2.3 Agent 设计                                                                                                                                                                                                                                    
                                                                                                                                                                                                                                                    
  2.3.1 ReAct Agent                      
                                                                                                                                                                                                                                                    
  FinQAAgent 继承 ToolAgent，采用 ReAct（Reasoning + Acting）范式：
  - System Prompt 定义角色为"Expert Financial Analyst"
  - 核心工作流： PLANNING（<plan> 标签）→ get_table_names → get_table_info → sql_query → calculator → FINAL ANSWER                                                                                                                                  
  - 每次工具调用后必须写 <reflection> 块，验证数据正确性                                                          
  - 最大 20 步交互

  2.4 训练方法                                                                                                                                                                                                                                      
                                                                                                                                                                                                                                                    
  2.4.1 算法：GRPO（Group Relative Policy Optimization）                                                                                                                                                                                            
                                                                                                                                                                                                                                                    
  - 对同一任务生成 n=8 个 rollout（group_size=8）                                                                                                                                                                                                   
  - 组内计算相对优势（advantage），无需 critic 网络                                                                                                                                                                                                 
  - 使用 verl 框架的 AgentWorkflowPPOTrainer                                                                                                                                                                                                        
                                         
  2.4.2 奖励函数（官方版本）                                                                                                                                                                                                                        
                                         
  单表： LLM-as-Judge 二值判定（True/False），Judge 输出 {True/False, 'Reason'}                                                                                                                                                                     
  - 判定规则：数学等价判断，处理减少/百分比格式、分数、小数容差（第一位小数）、小数-百分比等价                                                                                                                                                      
                                                                                                                                                                                                                                                    
  多表： LLM-as-Judge Rubric 评分（4个维度，各0-5分）                                                                                                                                                                                               
  - Primary Data Extraction（0.4权重）                                                                                                                                                                                                              
  - Derived Metrics & Math（0.4权重）— 含"级联错误协议"（Cascading Error Protocol）
  - Qualitative Reasoning（0.1权重）                                                                                                                                                                                                                
  - Internal Consistency（0.1权重）      
  - 加权归一化到 [0, 1]，阈值 ≥ 0.9 判定为 correct                                                                                                                                                                                                  
                                                                                                                                                                                                                                                    
  官方 Judge 模型： gpt-5-nano（blog 中提到使用 Portkey 缓存，~40% 命中率，Judge 成本约 $40）

  2.5 关键发现与消融实验                                                                                                                                                                                                                            
                                         
  2.5.1 "Terence Tao" 悖论                                                                                                                                                                                                                          
                                         
  任务成功依赖于纪律性、可重复的工具调用，而非开放式推理。大模型反而失败，因为：                                                                                                                                                                    
  - Schema 幻觉 — 猜测表名/列名而不是调用 get_table_names()/get_table_info()
  - 上下文洪泛 — 执行 SELECT * 导致上下文溢出                                                                                                                                                                                                       
  - 无错误恢复 — 重复失败策略而不阅读错误信息
                                                                                                                                                                                                                                                    
  2.5.2 消融实验 1：简单数据教会复杂技能

  三、我的改进详解                                                                                                                                                                                                                                  
                                                                                                                                                                                                                                                    
  基于官方 SOTA 方法，我在以下 6 个方面进行了改进，并设计了 3 组对照实验（finqa-grpo-incur、finqa-grpo-neg、finqa-grpo-nopen）进行消融验证。                                                                                                        
                                                                                                                                                                                                                                                    
  3.1 改进一：自适应课程学习采样器       
                                                                                                                                                                                                                                                    
  动机：                                 
  官方消融发现"仅单表训练"最优，课程学习（64.8%）不如纯单表（66.3%）。但我认为官方的课程学习可能过于粗糙——简单地按预设顺序引入难度，没有根据模型实际学习状态动态调整。如果课程采样权重能感知模型进步速度和饱和程度，应该能发挥课程学习的潜力。      
                                                                                                                                                                                                                                                    
  实现： finqa_curriculum_sampler.py（421行），包含 SourceTracker、CurriculumController、FinQACurriculumSampler 三个组件。                                                                                                                          
                                                                                                                                                                                                                                                    
  3.1.1 SourceTracker：滑动窗口成功率追踪
                                                                                                                                                                                                                                                    
  @dataclass                                                                                                                                                                                                                                        
  class SourceTracker:                   
      success_threshold: float = 1.0   # 单表 ≥1.0; 多表可覆写                                                                                                                                                                                      
      window_size: int = 512           # 滑动窗口大小
      recent_outcomes: deque           # 二值化结果 (1=成功, 0=失败)                                                                                                                                                                                
      rate_history: list[float]        # 成功率历史快照（最近20次）                                                                                                                                                                                 
                                                                                                                                                                                                                                                    
  - 异构奖励处理： 单表奖励是离散的 {0, 1}，多表奖励是连续的 [0, 1]。通过 success_threshold 参数统一二值化（单表阈值=1.0，多表阈值=0.8）                                                                                                            
  - 改进速度（Improvement Velocity）计算：                                                                                                                                                                                                          
                                                                                                                                                                                                                                                    
  $$v_s = \overline{r}{recent} - \overline{r}{early}$$                                                                                                                                                                                              
                                                                                                                                                                                                                                                    
  将成功率历史分为前半段和后半段，取均值之差。正值表示该数据源仍在改善，零/负值表示已饱和。                                                                                                                                                         
                                                                                                                                                                                                                                                    
  3.1.2 CurriculumController：多信号采样权重计算                                                                                                                                                                                                    
                                                                                                                                                                                                                                                    
  核心公式：                                                                                                                                                                                                                                        
                                         
  $$\text{score}(s) = \left(v_s^+ + 0.1\right) \cdot (1 - \text{rate}_s) + \text{UCB}_s$$                                                                                                                                                           
                                         
  其中：                                                                                                                                                                                                                                            
  - $v_s^+ = \max(0, v_s)$ — 改进速度（截断负值），衡量该数据源是否仍在进步
  - $(1 - \text{rate}_s)$ — 提升空间，成功率越低说明越需要训练                                                                                                                                                                                      
  - $0.1$ — 基线常数，保证即使速度为0也有基础权重             
  - $\text{UCB}_s = 0.5\sqrt{\frac{2\ln(N+1)}{n_s+1}}$ — UCB探索奖励，防止某数据源被忽略                                                                                                                                                            
                                                                                        
  饱和抑制机制： 当某数据源成功率超过阈值（0.75）时，平滑衰减其权重：                                                                                                                                                                               
                                         
  $$\text{multiplier} = \max\left(0.4,\ 1.0 - 3.0 \cdot (\text{rate}_s - 0.75)\right)$$                                                                                                                                                             
                                                                                                                                                                                                                                                    
  $$\text{score}(s) \leftarrow \text{score}(s) \times \text{multiplier}$$                                                                                                                                                                           
                                                                                                                                                                                                                                                    
  这意味着当成功率从 0.75 升到 0.95 时，乘数从 1.0 平滑降到 0.4。                                                                                                                                                                                   
                                                                                                                                                                                                                                                    
  最终权重： 对所有数据源的 score 做 Softmax 归一化（温度 τ=0.8），并设置最低权重下限 0.1 防止饿死：                                                                                                                                                
                                         
  $$w_s = \text{softmax}\left(\frac{\text{score}(s)}{\tau}\right), \quad w_s \leftarrow \max(w_s, 0.1)$$                                                                                                                                            
                                         
  然后重新归一化。                                                                                                                                                                                                                                  
                                         
  3.1.3 负样本固定注入                                                                                                                                                                                                                              
                                         
  负样本不参与课程学习权重调整，而是每个 batch 固定注入：                                                                                                                                                                                           
  - 40 条单表负样本 + 10 条多表负样本    
  - 剩余位置（384 - 50 = 334 条）由课程采样的正样本填充                                                                                                                                                                                             
                                                       
  每个 batch 的组成：[负样本(50)] + [课程采样正样本(334)]，batch 内随机打乱避免位置偏差。                                                                                                                                                           
                                         
  3.2 改进二：负样本训练（不可回答问题）                                                                                                                                                                                                            
                                         
  动机： 官方方法只训练"能回答的问题"。但实际场景中，用户可能提出数据中不存在的问题。如果模型无法识别这种情况，会产生幻觉。负样本训练教会模型说"我不知道"。                                                                                         
                                                                                                                                                                                                                                                    
  3.2.1 负样本生成 Pipeline                                                                                                                                                                                                                         
                                                                                                                                                                                                                                                    
  正样本 Q&A 对 + 表格 Schema                                                                                                                                                                                                                       
      ↓  (Qwen3-235B 生成)               
  负样本问题（3种篡改策略）                                                                                                                                                                                                                         
      ↓  (Qwen3-235B 验证)               
  验证确实无法回答 → 保留                                                                                                                                                                                                                           
                                                                                                                                                                                                                                                    
  三种篡改策略：                                                                                                                                                                                                                                    
  1. Time Travel（时间穿越）： 询问表格中不存在的年份/时期。如表格有2020-2022数据，问2023年                                                                                                                                                         
  2. Metric Hallucination（指标幻觉）： 询问相关但不存在的指标。如表格有Gross Margin，问EBITDA Margin                                                                                                                                               
  3. Granularity Mismatch（粒度不匹配）： 询问不存在的分解维度。如表格只有合并总数，问特定地区                                                                                                                                                      
                                                                                                                                                                                                                                                    
  生成与验证：                                                                                                                                                                                                                                      
  - 使用 VLLMClient 本地部署的 Qwen3-235B                                                                                                                                                                                                           
  - 160 个并发 worker（ThreadPoolExecutor）
  - 生成后由独立验证 prompt 确认问题确实无法回答（can_answer: false）                                                                                                                                                                               
  - 所有负样本答案统一为 [DATA_UNAVAILABLE]                                                                                                                                                                                                         
                                                                                                                                                                                                                                                    
  3.2.2 负样本奖励设计                                                                                                                                                                                                                              
                                                                                                                                                                                                                                                    
  负样本使用字符串匹配而非 LLM Judge（节省成本、避免歧义）：                                                                                                                                                                                        
                                                                                                                                                                                                                                                    
  is_correct = "DATA_UNAVAILABLE" in final_answer.upper()                                                                                                                                                                                           
  reward = 1.0 if is_correct else 0.0                                                                                                                                                                                                               
  # 同样施加步数惩罚                                                                                                                                                                                                                                
  final_reward = reward - num_steps * 0.01                                                                                                                                                                                                          
                                                                                                                                                                                                                                                    
  3.3 改进三：步数惩罚（效率奖励塑形）                                                                                                                                                                                                              
                                                                                                                                                                                                                                                    
  动机： 官方方法只关注最终正确性，不鼓励效率。模型可能用很多冗余步骤（反复查询、试错）达到正确答案。步数惩罚引导模型用更少的步骤完成任务。                                                                                                         
                                                                                                                                                                                                                                                    
  公式：                                                                                                                                                                                                                                            
                                                                                                                                                                                                                                                    
  $$R_{final} = R_{judge} - n_{steps} \times \lambda$$                                                                                                                                                                                              
                                         
  其中 $\lambda = 0.01$（STEP_PENALTY_COEF）。                                                                                                                                                                                                      
                                         
  设计考量：                                                                                                                                                                                                                                        
  - 系数 0.01 足够小，不会让正确但步数多的轨迹得到负奖励（20步最大扣0.2，而正确答案得1.0）
  - 但在 GRPO 的组内相对比较中，同样正确的轨迹中步数少的会获得更高的 advantage                                                                                                                                                                      
  - 对负样本同样施加，鼓励模型快速判断数据不可用                              
                                                                                                                                                                                                                                                    
  3.4 改进四：工具成功率追踪             
                                                                                                                                                                                                                                                    
  动机： 官方方法只看最终结果，无法诊断模型在哪个工具上犯错最多。细粒度工具追踪为训练过程提供可解释性。
                                                                                                                                                                                                                                                    
  实现： 在 FinQAEnvironment._execute_tool_calls() 中拦截每次工具调用，记录：                                                                                                                                                                       
  - accessed_tables：追踪 get_table_info 访问了哪些表                                                                                                                                                                                               
  - tool_stats：每个工具的 success/fail 计数                                                                                                                                                                                                        
  - num_tool_calls：总调用次数                                                                                                                                                                                                                      
                                                                                                                                                                                                                                                    
  在 reward 函数中，还通过解析 ReAct 轨迹文本（_compute_tool_success_rates）补充最后一轮的工具统计：
                                                                                                                                                                                                                                                    
  # 5个追踪维度 × 4种数据源 = 20组指标   
  ALL_TOOLS = ["sql_query", "get_table_info", "get_table_names", "calculator", "format_error"]                                                                                                                                                      
  prefixes = ["single_table", "multi_table", "negative_single_table", "negative_multi_table"]                                                                                                                                                       
  # 每组包含 {prefix}_{tool}_success_rate 和 {prefix}_{tool}_calls                                                                                                                                                                                  
                                                                                                                                                                                                                                                    
  3.5 改进五：增强的奖励函数（fin_qa_reward_doubao.py）                                                                                                                                                                                             
                                                                                                                                                                                                                                                    
  动机： 官方使用 gpt-5-nano / Dashscope qwen3.5-flash 作为 Judge，成本较高且不稳定。我切换到 Doubao（豆包，字节火山引擎）和本地 vLLM 部署的模型，并增加鲁棒性。                                                                                    
                                                                                                                                                                                                                                                    
  改进点：                                                                                                                                                                                                                                          
  1. 双 API 支持： 通过 FINQA_JUDGE_API_TYPE 环境变量切换 Responses API（Doubao 云端）和 Chat Completions API（本地 vLLM）                                                                                                                          
  2. 重试逻辑： 3次重试，带抖动退避（(attempt * 2) + random.uniform(1.0, 5.0)）                                                                                                                                                                     
  3. Judge 统计： 追踪 judge_request_ok、judge_client_unavailable、judge_timeout_error、judge_api_error、judge_parse_error、judge_fallback_error
  4. Thinking 模型兼容： 自动去除 <think>...</think> 块

  四、改进的设计哲学总结                 
                                                                                                                                                                                                                                                    
  1. 课程学习不是没用，而是需要自适应： 官方结论是课程学习不如纯单表，但这是因为静态课程无法感知模型学习状态。自适应课程通过多信号（改进速度 + UCB探索 + 提升空间 + 饱和抑制）动态调整权重，让模型在"有提升空间"的难度级别上多花时间。
  2. 二值奖励 + 轻量效率塑形： 保留官方发现的"二值优于部分奖励"结论，但通过极小的步数惩罚系数（0.01）引入效率信号——不改变正确性判定，只在同等正确的轨迹间偏好更高效的。                                                                             
  3. 负样本是安全性保障： 现实场景中模型必须知道"何时说不知道"。通过系统化的负样本生成（3种策略 + 双重验证）和字符串匹配奖励（低成本、无歧义），教会模型识别不可回答的问题。
  4. 可观测性驱动迭代： 工具级别的成功率追踪、Judge 统计、细粒度指标日志——这些不直接提升模型性能，但为诊断问题和指导下一步改进提供了数据基础。

  项目简介                                                                                                                                                                                                                                          
                                                                                                                                                                                                                                                    
  基于强化学习（GRPO）训练 ReAct 风格的工具调用 Agent，回答 SEC 10-K 年报中的定量金融问题。Agent 配备 4 个金融工具（表检索、Schema 查看、SQL 查询、计算器），通过 LLM-as-Judge 提供奖励信号进行端到端 RL 训练。官方 SOTA 结果：仅 4B 参数的模型在   
  FinQA benchmark 上达到 59.7% Pass@1，超越 Qwen3-235B（51.4%），接近 Gemini 2.5 Pro（60.6%）。                                                                                                                                                     
                                                                                                                                                                                                                                                    
  我的工作与贡献                                                                                                                                                                                                                                    
                                                                                                                                                                                                                                                    
  在官方 SOTA 训练方法基础上，我从课程学习、奖励塑形、鲁棒性训练、评测体系四个维度进行了系统性改进：
                                                                                                                                                                                                                                                    
  1. 自适应课程学习采样器                                                                                                                                                                                                                           
  - 官方消融显示静态课程学习不如纯单表训练。我设计了多信号自适应课程控制器，融合改进速度（improvement velocity）、UCB 探索奖励、提升空间权重和饱和抑制机制，通过 Softmax 温度归一化动态调整各难度级别的采样权重。核心公式：$\text{score}(s) = (v_s^+
   + 0.1)(1 - \text{rate}_s) + 0.5\sqrt{2\ln N / n_s}$，高成功率数据源自动降权（乘数从 1.0 衰减至 0.4）。                                                                                                                                           
                                                                                                         
  2. 负样本训练与生成 Pipeline                                                                                                                                                                                                                      
  - 设计了系统化的负样本（不可回答问题）生成流程：基于 3 种篡改策略（时间穿越、指标幻觉、粒度不匹配）用 Qwen3-235B 生成 + 独立验证，确保问题确实无法从数据中回答。训练时每 batch 固定注入 50
  条负样本（不参与课程学习），使用字符串匹配奖励（低成本、无歧义），教会模型识别边界并输出 [DATA_UNAVAILABLE]。                                                                                                                                     
                                                                                                               
  3. 效率奖励塑形（Step Penalty）                                                                                                                                                                                                                   
  - 在保留二值正确性奖励的基础上，引入轻量步数惩罚（$R = R_{judge} - 0.01 \times n_{steps}$），在 GRPO 组内相对比较中偏好更高效的轨迹。系数足够小不影响正确性判定，但有效引导模型减少冗余工具调用。                                                 
                                                                                                                                                                                                                                                    
  4. 完整评测基础设施与消融实验                                                                                                                                                                                                                     
  - 构建了多模型自动化评测框架：FSDP 分片自动合并、vLLM 服务自动部署/回收、Judge 模型独立部署。设计 3 组对照实验（+课程学习、+负样本、+步数惩罚的各种组合）与官方模型对比，评测指标与训练 validation                                                
  完全一致，结果按条保存含完整对话、各维度分数和工具级统计。
